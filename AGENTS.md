# Contributor & AI-Agent Guide

Guidance for anyone — human or AI coding agent — proposing changes to SatChecker.
Following this keeps review focused on the substance of a change instead of
style and process nits. CI enforces most of the style rules below, so a PR that
ignores them will simply fail its checks.

Human contributors: start with [CONTRIBUTING.md](.github/CONTRIBUTING.md) for
project setup, docstring style, and licensing. This file is the detailed
command and constraint reference that complements it.

## Project

SatChecker is a Python 3.11 satellite-tracking API (Flask + SQLAlchemy, Redis
cache, Celery). Application code lives under `src/`.

## Repository layout

- `src/api/` — the Flask API. Notable subpackages: `entrypoints/` (routes),
  `services/` (business logic), `adapters/` (repositories, external data
  sources), `domain/`, `middleware/`, `utils/`, `migrations/` (Alembic),
  `changes/` (changelog fragments).
- `src/data/` — data-collection/pipeline scripts (TLE / ephemeris ingestion).
- `tests/` — the pytest suite; mirror the package you're changing.

## Before opening a PR — run these locally

The repo is configured for `pre-commit`; the fastest path is to install it once
and let it run on every commit:

```bash
pip install pre-commit && pre-commit install
```

Or run the tools directly (they must all pass):

```bash
black .              # formatting (line length 88, target py311)
ruff check --fix .   # linting
mypy .               # type checking
pytest               # tests
```

CI runs `black --check`, `ruff check`, `mypy`, and `pytest` on every pull
request. These are the same tools; if they pass locally they pass in CI.

## Style constraints

- **Do not hand-format.** Let `black` format the code; don't fight it.
- **Do not reformat or rewrite code unrelated to your change.** Keep the diff
  limited to the lines your fix actually needs. Unrelated reformatting,
  import reordering, or renaming makes review much harder.
- **Match the surrounding code** — naming, structure, and comment density of the
  file you're editing.
- **Use Google-style docstrings** — see [CONTRIBUTING.md](.github/CONTRIBUTING.md)
  for an example.

## Scope & process constraints

- **One issue/concern per PR.** Small, focused PRs get reviewed and merged
  faster. Split unrelated changes.
- **Add or update tests** for behavior changes; put them under `tests/`.
- **Don't add dependencies** or do broad refactors without opening an issue to
  discuss first.
- **Don't make optimizations or changes unrelated to the requested fix.** If you
  spot something else worth improving, check first — open an issue or raise it in
  the PR with justification — rather than bundling it into the change.
- **Target the `develop` branch**, not `main`. Changes are validated in a test
  environment from `develop` before being promoted to production.
- **Commit messages:** short imperative summaries, capitalized, no type prefix
  (e.g. `Fix cache errors during Redis restarts`). Match the existing history.

## Database changes

Schema or model changes require an Alembic migration. Generate it the same way
deploys apply migrations (from `src/api/`):

```bash
cd src/api && alembic -c migrations/alembic.ini revision --autogenerate -m "describe change"
```

Migrations are applied automatically on deploy (`alembic upgrade head`). Don't
hand-edit a migration that has already been merged.

## Don't edit these directly

- `changes.md` — the compiled changelog, generated by `towncrier` from the
  fragments in `src/api/changes/`. Edit the fragments, not the compiled file.
- Already-merged Alembic migrations in `src/api/migrations/versions/`.
- Generated output — `__pycache__/`, `htmlcov/`, `.mypy_cache/`; never commit these.
- Dependency versions — bumps are handled by Dependabot; don't upgrade packages
  in a feature PR.

## Changelog fragment (required for code changes)

`towncrier` requires a changelog fragment for changes under `src/*.py`, and a
pre-commit hook checks for it. Add a file:

```
src/api/changes/<PR-number>.<type>.md
```

where `<type>` is one of: `feature`, `bugfix`, `changed`, `removal`, `doc`,
`misc`. The file contains one human-readable sentence describing the change,
e.g.:

```
src/api/changes/241.bugfix.md
--------------------------------
Fixed cache errors during Redis restarts by falling back to the database.
```

## Good to know

- Prod depends on Redis (cache), Postgres (data), and Celery (tasks).
- **Redis is a cache, not a source of truth.** Code must fall back to Postgres
  when a cache read misses or Redis is unreachable — never assume a cached value
  is present, and never make Redis a hard dependency for a request to succeed.
- Keep secrets and environment-specific values out of the codebase.
